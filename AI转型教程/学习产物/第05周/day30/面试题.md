## Q1(当日新知·"为什么") 为什么强调 API key 必须从环境变量读、绝不硬编码进 .py?"零硬编码"防的到底是什么?key 缺失时用 raise SystemExit 与 return 退出有何区别?
考点:密钥安全(不入代码/不提交仓库)+ 优雅退出的机制;os.environ 与 process.env 的差异;我的回答:

api 是身份唯一标识，用于模型识别付费。硬编码相当于把付费账号明文放入代码库，如果发生泄漏，将造成损失。
Git 历史删不掉：即使你后来删掉那行代码，Key 仍然留在 commit 历史里。

防的：机器扫描 或意外泄漏造成损失

| 方式 | 作用范围 | 是否终止进程 | 适用场景 |
|---|---|---|---|
| `return` | 当前函数 |  否 | 正常返回、守卫式提前退出 |
| `raise SystemExit` / `sys.exit()` | 整个进程 | 是 | CLI 脚本遇到不可恢复错误时退出 |


## Q2(往期复习·易错) 第04周 Day23 你写过 http_fetcher.py。为什么每个 requests 请求都必须显式设置 timeout?不设 timeout 而对端迟迟不响应时,程序会怎样?这与你 JS 里 fetch 的默认行为有何异同?
考点:超时红线(day23 验收口径)、阻塞与资源占用、Timeout 异常;JS fetch 默认也无超时(AbortController 手动控制);我的回答:
equests 默认 timeout=None
不设置Timeout，请求就会无限等待返回。如果请求丢失或网络波动导致请求永远无法返回。就会线程/进程卡死在那里，浪费资源。

和fetch 模型行为没有不同。不同的是，fetch 可以AbortController 手动结束请求。而且浏览器都有兜底机制，Chrome：网络请求约 300 秒后超时，Firefox：约 90 秒后超时。

## Q3(往期复习·阅读说输出) 第03周异常体系。说出以下代码的打印顺序,并解释 else 为什么没执行、finally 为什么在有 return 时仍执行:
```python
def f():
    try:
        print("A")
        return "B"
    except Exception:
        print("C")
    else:
        print("D")
    finally:
        print("E")

print(f())
```
考点:try/except/else/finally 执行时机、return 与 finally 的交互;我的回答:
打印顺序：A E B
为什么else 没有执行，因为走到try 时， print("A") 打印完，return "B" 结束了程序，所以不会执行else
为什么执行finally,因为finally 的执行时机是函数销毁前，无论对错，都会执行

# 参考答案(2026-11-18 闭卷作答并对答案后补录)

## Q1 参考要点 ✅ 优

**为什么 key 必须从环境变量读、绝不硬编码:**
- key 是**凭证(credential)**而非仅身份标识——标识可公开,凭证必须保密;它绑定付费账号,泄漏=别人花你的钱。
- 硬编码=明文进代码库,泄漏渠道:①公开仓库被爬虫/机器扫描秒抓;②**Git 历史删不掉**——后来删掉那行,key 仍留在 commit 历史里;③私有仓库也不安全——协作者、CI/CD 日志、fork 都可能暴露。
- 落地姿势:`.env` 存 key + `.gitignore` 排除 + `os.getenv` 读取(day30 产物即此模式)。

**raise SystemExit vs return:**

| 方式 | 作用范围 | 是否终止进程 | 适用场景 |
|---|---|---|---|
| `return` | 当前函数 | 否 | 正常返回、守卫式提前退出 |
| `raise SystemExit` / `sys.exit()` | 整个进程 | 是 | CLI 脚本遇到不可恢复错误时退出 |

- 加分点1:SystemExit 是 `BaseException` 的直接子类,与 `Exception` 是**兄弟**——`except Exception` 兜不住它,进程照常退出。
- 加分点2:`return None` 不报错但把 None 传给调用方,崩溃被推迟到下游(day30 首轮 P0 正是此病);SystemExit 的哲学是 fail fast——在出错的地方喊停。

## Q2 参考要点 ✅ 良

- requests 默认 `timeout=None`:不设则**无限等待**,对端不响应时线程/进程卡死,连接与资源被白白占用。超时后抛 `requests.exceptions.Timeout`(细分 `ConnectTimeout`/`ReadTimeout`)——面试要能说出"超时后我 catch 什么"。
- JS fetch 规范层**同样无默认超时**,行为模型一致;中止靠 `AbortController`(现代写法 `AbortSignal.timeout(ms)`)。
- 浏览器兜底(核验结论):Chrome 约 300 秒成立(Chromium 源码 `net/socket/client_socket_pool.cc` 连接池超时=5分钟);Firefox "90 秒"方向对但**别当精确常量**——超时分连接/响应/keep-alive 多阶段,各参数默认值随版本不同。面试稳妥说法:"浏览器有分钟级网络层兜底,但不可依赖——兜底触发前用户早已流失,且 Node 环境的 fetch 连这层兜底都没有"。
- 结论:无论 requests 还是 fetch,显式超时都是调用方的责任,不能指望运行时兜底。

## Q3 参考要点 ⚠️ 部分对(原答漏 B、机制解释需订正)

**实跑权威输出(已运行核验):**
```
A
E
B
```

- **漏了 B**:`return "B"` 不是终点——`f()` 返回后,外层 `print(f())` 还会打印返回值。完整顺序 A → E → B。
- **else 为什么没执行**:else 只在 try 块"无异常**且完整走完**"时执行;try 里一旦 `return`(或 break/continue)提前离开,else 就跳过。与"程序结没结束"无关——`return` 结束的是**函数**,不是程序。
- **finally 为什么仍执行**:函数真正把返回值交出去之前,无论走哪条路(正常结束/return/抛异常)都先执行 finally。执行序:算出返回值 "B" → 被 finally 截住 → print("E") → 才真正返回 "B"。
- 记忆锚点:finally 是"离席前必做的收尾",return 只是"起身",外套没穿完人不会出门。
