## Q1(当日新知·"为什么"文字题)with 与文件模式

1. `with open(path, "r", encoding="utf-8") as f:` 相比 `f = open(path)` 然后手动 `f.close()`,好在哪?为什么 day18 起统一用 with?
2. 读、写、追加三种场景分别用哪个模式字母?`"w"` 和 `"a"` 在"打开已存在的文件"时行为差在哪?
3. 读一个含中文的文本文件为什么不写 `encoding` 有时正常、有时乱码?`encoding="utf-8"` 起什么作用?

- 我的回答：
1.
```python
    with open(path, "r", encoding="utf-8") as f:
        f.read()
    
    # 等价于
    try:
        f = open(path)
        f.read()
    finally:
        if f:
            f.close()
```
好处：
a.代码更简单，减少了嵌套
b.不会因为代码中断 或者 漏写close 造成进程挂机，浪费资源

2. r读 w写 a追加。 w 打开文件，文件指针在文件头，写入会覆盖之前的文件。a打开文件，文件指针在文件尾部，写入会追加内容，不会覆盖之前的内容
3. encoding 决定"用哪套规则把磁盘上的字节翻译成 str"。不写 encoding 时，Python 用的是操作系统/区域设置决定的默认编码，它随平台、随机器、随文件来源变化——所以同一段代码，文件编码和默认编码对得上就正常，对不上就乱码或报错

## Q2(当日·阅读说输出)writelines 与逐行读取

下面代码跑起来会怎样?请说清 `writelines` 收到的元素类型要求,以及为什么最后要手动加 `\n`。

```python
with open("t.txt", "w", encoding="utf-8") as f:
    f.writelines(["第一行", "第二行", "\n第三行\n"])
# 再读回逐行打印
with open("t.txt", "r", encoding="utf-8") as f:
    for line in f:
        print(repr(line))
```

追问:如果往 `writelines([...])` 的列表里塞一个整数 `888`,会发生什么?

- 我的回答：
-  第一行打印：第一行第二行\n
-  第二行打印：第三行\n
-  
原因：
writelines 实际为循环调用write,内容不会自己换行。所以文字 第一行第二行 在一行,repr 打印换行符，不执行。故第一行： 第一行第二行\n。第二行 ：第三行\n。最后一个空行不读取，所以不展示
追问: 会报类型错误，888 之前的内容会写入缓冲区。writelines 只能接收字符串类型。

## Q3(往期复习·概念对比)read / readlines / for-line

`f.read()`、`f.readlines()`、`for line in f` 三种读法,分别在什么时候把内容放进内存、哪个适合"统计一个很大的文件的行数"?结合 day18 产物 `sum_art` 的写法说明你的取舍。

- 我的回答：
- f.read() 会一次性把所有内容放入内存
- f.readlines() 会一次性把所有内容放入内存，然后建立list,性能最差
- for line in f 惰性，每次迭代交付一行；底层按块预读
  所以 for line in f 适合读取大文件。所以sum_art 使用 for line in f 做统计

# 参考答案(对答案后补 · 2026-10-21)

## Q1 参考
1. **with 的优越性**:上下文管理器在代码块退出时无论正常还是报错都会自动调用清理(文件 close),不依赖手写 `f.close()`。好处=①少嵌套、更简洁;②不会因为中断路径漏写 close 致文件句柄泄漏/未刷盘。⚠ 你写的等价体 `finally: if f: f.close()` 有隐藏坑:若 `open()` 本身就抛错,`f` 未定义,`finally` 里 `if f` 反而 NameError;`with` 不依赖这种手写判断。
2. 模式:r 读 / w 写 / a 追加。**w 更准确的语义是“打开即清空(truncate)”**,不是“指针在头逐字节覆盖”;想读写保留内容用 `r+`。a 打开保留原内容,写入追到末尾。
3. text mode 下,encoding 决定“用哪套规则把磁盘字节解码为 str”。不写时用平台默认编码(Windows 常 GBK、Linux 常 UTF-8),随系统/区域变;UTF-8 中文文件碰上 GBK 默认就乱码或报 UnicodeDecodeError。显式写 `encoding="utf-8"` 就是把这个变量固定下来。

## Q2 参考
- 文件内容=`第一行第二行\n第三行\n`。逐行读回 + `print(repr(line))` 输出两行:`'第一行第二行\n'` 和 `'第三行\n'`。
- 原因:writelines 只是“循环调 write”的语法糖,**不会自动补换行符**;repr 把 `\n` 当字符显示而不渲染。
- 追问:塞 int `888` 会 `TypeError: write() argument must be str, not int`;**888 之前的元素已写入**,因为 with 退出时 close 会 flush 缓冲区——这正是“为什么靠 with 而非手写 finally”的又一个具体体现。

## Q3 参考
- `f.read()`:一次性把全部内容为一个大 str。
- `f.readlines()`:一次性全读 + 再拆成行列表,额外开销最大。
- `for line in f`:**惰性迭代,一行一行给**,底层按块预读(不是一字节一次系统调用),内存占用恒定。
- 大文件行数统计首选 `for line in f`(单遍累加计数器、不存整文件);sum_art 修正后的写法即此。

## Q4 参考
- 行A `2 2 2`;行B `100 2 2`。
- 机制:**读=双向查找(实例优先、找不到再上溯类);写=只落实例**。`c1.total = 100` 在实例上新建属性、遮蔽同名类属性,类属性本身未被修改(仍为原值)。
- 追问点:想让全局变→经类名改 `Counter.total = 100`;`self.total += 1` 在 `__init__` 里会先读类值再写实例导致分家(经典陷阱);`del c1.total` 可解除遮蔽。
